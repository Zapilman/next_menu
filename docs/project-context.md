# Контекст проекта

Учебный Next.js-проект: публичное QR-меню заведения. Цель — архитектурные решения App Router, которые можно объяснить на собеседовании. Не клон ChoiceQR и не продуктовый объём.

## Что решить до кода

- Какой срез продукта закрывает 9 критериев без лишних фич
- Что зритель уже знает и чего не повторять
- Насколько узким держать стек
- Когда начинать код: только после записей в [decisions.md](./decisions.md)

## Рекомендуемый дефолт

- Аудитория: Юра Здоров. Уже знает React, TypeScript, React Query, Zustand и SPA-стиль Next.js (pages/client-heavy). Не повторять основы этих вещей.
- Цель: Server Components, кэш, мутации, auth на сервере, streaming, SEO, прод-сборка — на одном узком продукте.
- Форма: фичи только как уроки. Урок = ссылка на Next.js docs + разбор подходов + как выбор меняет фичу. Код урока пишет Юра; агент — обсуждение, пример в чате и согласованная рутина.
- Продукт: одно заведение, полное меню, публичная страница. Тонкий кабинет — отдельным уроком после публичного среза.
- Стек: Next.js App Router + React + TypeScript, CSS Modules, SQLite. Без Tailwind, Zustand, React Query, NextAuth, UI-кита в фундаменте.

## Альтернативы

- Широкий продукт (корзина, заказы, оплата, несколько заведений) — больше кода, меньше фокуса на критерии.
- Сразу кабинет + NextAuth + React Query + Zustand — повторит знакомый SPA и спрячет RSC.
- Только теория без продукта — сложнее показать, как выбор бьёт по фиче.

## Компромиссы

- Узкий срез vs «настоящее» QR-меню: отрезаем заказы и доставку, оставляем каталог и заведение — этого хватает для рендера, кэша, SEO и (позже) auth.
- Не повторять React Query/Zustand сразу: потом один урок «SPA-контраст» на клиентской фиче, не как фундамент.
- Документы сейчас, код потом: можно сменить дефолты без переписывания приложения.
