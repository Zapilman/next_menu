# Цель и 9 критериев

Критерии — чеклист собеседования. Каждому — страница QR-меню и что сказать вслух. Код не писать, пока не зафиксированы решения.

Референс типов страниц: [ChoiceQR](https://idealist1.choiceqr.com/section:menyu/garbuzove-menyu) — заведение, раздел меню, блюда (название, цена, состав, вес, бейдж).

## Что решить до кода

- Какие 3–4 маршрута обязательны в первом срезе
- Какой критерий на какой странице демонстрируем, без дублирования
- Где граница «достаточно для интервью» vs продуктовый scope

## Рекомендуемый дефолт

Срез: публичная страница заведения + полный каталог меню. Кабинет — позже, только если нужен критерий 5 в коде.

| # | Критерий | Куда сажаем в QR-меню | Что объяснить |
|---|----------|------------------------|---------------|
| 1 | Server / Client Components, RSC Payload, hydration | Каталог — RSC (список блюд). Клиент — фильтр раздела, раскрытие состава. | RSC Payload ≠ hydration. Клиент гидратируется, серверные узлы — нет. |
| 2 | Стратегия рендера: каталог / кабинет / публичный профиль | Каталог и заведение — статика/ISR. Кабинет — dynamic. | Зачем гостю SSG, почему кабинет нельзя кэшировать как меню. |
| 3 | Request cache vs Data cache vs Full Route Cache vs клиентская навигация | Меню: `fetch`/data cache + Full Route Cache. Переход раздел→раздел: Router Cache. Кабинет: `no-store`. | Четыре слоя, не «просто cache». |
| 4 | Server Actions vs Route Handlers vs прямой доступ к данным | Чтение меню — прямо в RSC. Правка блюда в кабинете — Server Action. Route Handler — только если нужен HTTP (QR webhook нет). | Action — не REST. RSC может читать БД/JSON без API-слоя. |
| 5 | Auth и права без доверия клиенту | Кабинет: скрыть UI недостаточно. Проверка cookie/session в Action и в RSC. Гостевое меню — публичное. | `use client` не граница безопасности. |
| 6 | Streaming, Suspense, `loading.tsx`, ошибки | Оболочка заведения сразу, секции меню — Suspense. Нет раздела — `not-found`. Ошибка загрузки — `error.tsx`. | `loading.tsx` = route-level Suspense, не замена локальному. |
| 7 | SEO, bundle, как читать измерения | Metadata у заведения и раздела. Клиентский JS только на интерактиве. `@next/bundle-analyzer` — отдельный урок. | Что измеряем: RSC payload, JS клиента, TTFB vs First Contentful. |
| 8 | Прод-сборка, ключевые сценарии, деплой | `next build`: гость открыл QR → меню; персонал (позже) → кабинет. Деплой — Node/Vercel. | Отличие `next dev` от prod cache. |
| 9 | Архитектурные компромиссы | RSC-каталог vs SPA с React Query. JSON vs SQLite. Статика меню vs всегда свежее. | Нет единственного правильного стека — есть критерии. |

## Альтернативы

- Кабинет в первом срезе: раньше закрывает критерии 4–5, раздувает продукт.
- Только каталог без страницы заведения: слабее SEO и «публичный профиль».
- SPA-меню на клиенте: знакомо Юре, почти не закрывает 1–3 и 7.

## Компромиссы

- Один продукт на все 9 пунктов: проще рассказ, риск смешать уроки. Лечится форматом из [06-lessons.md](./06-lessons.md).
- Кабинет откладываем: критерий 5 сначала на словах и в docs, в коде — когда дойдём.
- Карточка блюда как отдельный URL: плюс для SEO и `generateStaticParams`; минус — лишний маршрут. Каталог с деталями в списке тоже закрывает RSC/hydration.

## Открытые вопросы

- Первый срез: только ` / ` + `/menu` или сразу `/menu/[section]`?
- Критерий 5 в коде в уроке 1 или отдельным уроком после публичного меню?
- Отдельный URL блюда нужен для урока `generateMetadata` / `generateStaticParams`?
